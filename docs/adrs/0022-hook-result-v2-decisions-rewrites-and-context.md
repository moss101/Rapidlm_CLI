# ADR 0022 — Hook result v2: decisions, input rewrites and additional context through the existing approval and tool paths

**Status:** Accepted for `SEAMS-RAPIDLM-01` (Phase 0; governs `SEAM-01`, consumed by `SEAM-05`, `SEAM-09`, `SEAM-11`)  
**Date:** 2026-09-20  
**Baseline audit:** [SEAM-00-1](../goals/seams-phase0-baseline-2026-09-20.md) §3 (SEAM-01)  
**Builds on:** ADR 0002 (event-sourced durable state), 0010 (capability leases), 0017 (WASM plugin default), 0018 (protocol adapters are not authorities); governing document [`SEAMS §3.2 S1–S5`](../goals/seams-governing-principles.md)

## Context (what exists at the baseline)

Two hook systems exist and neither is a policy seam today:

- **Production hooks** — `apps/rapid/src/hooks.rs`: eight command-list stages parsed from project settings (`pre_tool_use`, `post_tool_use`, `session_start`, `session_end`, `subagent_start`, `subagent_stop`, `pre_compact`, `post_compact`). A `pre_tool_use` hook receives `{"tool","arguments"}` on stdin; a non-zero exit, a crash or a timeout **denies** with the hook's output as the model-visible detail (`run_pre_tool_hooks`, `exec_tools.rs:2353`). The other stages are notification-style (`run_notify_hooks`), never gate. `run_hook_once` redirects the hook's **stdout and stderr into one temp file**, so today a hook has no channel that could carry a structured result.
- **Plugin hooks** — `crates/plugin-host/src/hooks.rs`: a 27-event `HookEvent` engine (`ToolPre`, `ToolPost`, `ToolFailure`, `PermissionRequest`, `AgentStart/Stop`, …; `crates/plugin-host/src/hooks.rs:154–182`) with `HookSpec { matcher, timeout, failure_policy, requested_caps, sandbox }`, a `{"decision":"block"}` stdout parser (`parse_hook_output`), grant-attempt detection (invariant 13) and lease-gated execution through the process supervisor. It is reachable only from `rapid plugins hook-test` (a fixture dry-run); nothing in the exec loop dispatches it.

The exec loop already has the durable Human/Approval wait a hook `ask` needs: `permissions::Decision::Ask` → `ToolStepResult::ApprovalRequired` → the `SuspendedTurn` is persisted as the `approval.requested` payload → `TurnOutcome::Waiting` releases the lease → resolution (`/approvals`, ACP `acp_resolve_and_continue`) replays the suspension and executes the call exactly once (`apps/rapid/src/approvals.rs` module doc). `JsonlExitCode::NeedsApproval = 10` is the documented "needs a human" exit (`headless/jsonl.rs:104`).

## Decision

1. **One versioned result type, owned by `crates/protocol`.** `protocol::hooks::HookResult` (`schema = "rapidlm.hook_result"`, `version = 2`) is the wire shape a hook may print on **stdout**: `decision ∈ {allow, deny, ask, defer}`, `reason: Option<String>`, `updated_input: Option<Map>`, `additional_context: Option<String>`, `hook_specific: Option<Map>`. Unknown fields are ignored (additive evolution); a schema fixture lives under `crates/protocol/tests/fixtures/hooks/v2/`. The plugin-host engine's existing `"block"` token is accepted by the shared parser as a synonym of `deny` so that engine's tests keep their meaning; new hooks write the four v2 words.
2. **v1 semantics are the absence of a result.** A production hook that prints nothing parseable on stdout keeps today's contract byte-for-byte: exit code decides, stderr is the detail. `run_hook_once` therefore separates the two streams (stdout → result candidate, stderr → detail) and the pre-tool timeout/crash/malformed-output rules stay **deny**. Notification stages stay fail-open with a recorded warning.
3. **`ask` is the existing approval wait, not a new one.** A pre-tool `ask` is mapped onto `Decision::Ask` for that call with the hook's `reason` carried into the `ApprovalRequest` summary and the `approval.requested` payload (`source: "hook:<id>"`). Everything downstream — `approval.requested` → `tool.approval_required` (the `SuspendedTurn`) → `turn.interrupted[ApprovalPending]` → `/approvals` or ACP resolution → `approval.resolved` → continuation turn — is the existing path (S2, invariant 14). Headless `rapid exec` builds its tools without an approval sink today (`interactive.rs:8633–8636`), so a permission `Ask` becomes a model-visible `Denied(ModeAsk)` and the turn continues; that behaviour is unchanged (S11). A hook `ask` in headless is new behaviour and therefore gets the documented contract: the wait is recorded exactly as the TUI records it, the turn ends, and the process exits `NeedsApproval` (10) — never an implicit allow. It is resolved from a surface that can decide — `rapid resume <session>` then `/approvals`, or an ACP client; `rapid exec --continue` starts a new turn and does not resolve a pending approval (a headless `rapid approvals approve|deny` command is a SEAM-10 candidate). Unattended runs under a forced mode (`rapid cron`) install no hook-ask sink and keep the stated denial: a parked turn nobody resumes is worse.
4. **`defer` is "no opinion".** The call proceeds to the normal permission evaluation; the decision is still recorded (`hook.decided` event with `decision: defer`).
5. **Rewrites are validated, journaled and marked (S3).** `updated_input` replaces the call's arguments only after the rewritten arguments pass the same argument parser the tool uses at execution (`exec_tools` per-tool `parse_*_args`, `exec_tools.rs:2371–2385`, and the `MAX_TOOL_ARGUMENTS_BYTES` bound); a failure **denies naming the hook**. The governing document names `crates/tool-gateway` validation here; the audit found that crate is not a dependency of `apps/rapid` and `ExecTools::validate` is a pass-through (`exec_tools.rs:6927–6938`), so the per-tool parsers are the real contract today and wiring `tool-gateway` is out of this item's scope. The last rewriting hook wins; a `deny` from any hook discards every rewrite. A `hook.input_rewritten` ledger event carries hook id, `sha256(before)`, `sha256(after)` and both bounded inputs; the transcript gets one line `[hook <id> rewrote <tool> input]`. The permission decision is evaluated on the **rewritten** input (what will actually run).
6. **`additional_context` is untrusted tool-shaped content (S4).** It is appended *after* the tool result inside the fence the model already knows for untrusted material — `<untrusted_context locator="hook:<id>">…</untrusted_context>` (`apps/rapid/src/model.rs:530–537` uses this shape for `TrustClass::Untrusted` context blocks) — bounded by `MAX_HOOK_CONTEXT_BYTES` (4 KiB, the `MAX_READ_BYTES` ceiling; the audit found no single "tool-output ceiling" — bounds are per tool: 256 B detail, 4 KiB read, 8 KiB search, 16 KiB shell), and passes through the same redaction the result does. Instructions inside it are data.
7. **New events are stages of the same config, not a new engine.** `user_prompt_submit` (may deny with a reason; a queued prompt whose hook denies stays queued and the reason is shown), `stop_cancelled` (fires *instead of* `stop` when a turn ends without completing — interrupt, denied permission, budget, max turns — and carries `reason`), `subagent_stop` gains the ability to block (v2 `deny` holds the child's completion for the parent to see), `post_tool_use_failure` (dispatch failure or an MCP error result; may add context, cannot block). Existing `session_start/end`, `pre/post_compact`, `subagent_start` stages are unchanged. `stop` is a new stage that fires on a completed turn; the pair is exclusive by construction (one `TurnEnd` site chooses which).
8. **Managed policy narrows hooks.** `hooks.managed_only = true` runs only the hook lines the managed policy itself declares; `hooks.denied_events = [..]` skips stages by name. Both are gates in `managed_config.rs` reported with field/origin/remediation like the existing ones (S5).
9. **Provenance for every decision.** Every v2 decision — `allow` included, so AC-02's "ledger record" holds for all four words — appends `hook.decided` (`rapidlm.hook.decision/v1`: hook position `pre_tool_use[<n>]`, a 12-hex digest of the command line, event, decision, reason digest, grant-attempt flag, tool, call id). v1 hooks produce no record. In the transcript, `allow` and `defer` are silent; only a blocking or failing hook shows a line.

## What is deliberately not done

- The plugin-host `HookSpec` engine is **not** wired into the exec loop by this ADR. Its matcher, sandbox and lease model are the right long-term executor, but reaching it requires a lease at the call site (`sandbox_exec.rs`'s ceremony is the one production lease-minting path). The shared `protocol::hooks::HookResult` is the bridge: when the engine is wired later it parses the same shape. A second parser or a second decision enum is forbidden.
- No hook may grant a capability; a v2 object with grant-shaped keys is a recorded warning and the keys are ignored, as `plugin_host::hooks::is_grant_key` does today (invariant 13).

## Consequences

- `apps/rapid/src/hooks.rs` changes shape (separated streams, result parsing, new stages) and its module doc and constants lose the peer-product references they carry today (rule 2.4).
- `SEAM-05` (plan approval) and `SEAM-11` (elicitation) reuse decision 3's mapping onto the approval wait rather than adding a wait of their own.
- `docs/reference/event-catalog.md` gains `hook.decided`, `hook.input_rewritten`; `sdk/typescript/schemas/wire.v1.json` gains the same kinds (the SDK catalog is hand-maintained; there is no Rust→catalog drift test, so the delivery record names both edits).
