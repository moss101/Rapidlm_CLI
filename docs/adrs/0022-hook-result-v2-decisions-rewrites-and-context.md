# ADR 0022 — Hook result v2: decisions, input rewrites and additional context through the existing approval and tool paths

**Status:** Accepted for `SEAMS-RAPIDLM-01` (Phase 0; governs `SEAM-01`, consumed by `SEAM-05`, `SEAM-09`, `SEAM-11`)  
**Date:** 2026-09-20  
**Baseline audit:** [SEAM-00-1](../goals/seams-phase0-baseline-2026-09-20.md) §3 (SEAM-01)  
**Builds on:** ADR 0002 (event-sourced durable state), 0010 (capability leases), 0017 (WASM plugin default), 0018 (protocol adapters are not authorities); governing document [`SEAMS §3.2 S1–S5`](../goals/seams-governing-principles.md)

## Context (what exists at the baseline)

Two hook systems exist and neither is a policy seam today:

- **Production hooks** — `apps/rapid/src/hooks.rs`: eight command-list stages parsed from project settings (`pre_tool_use`, `post_tool_use`, `session_start`, `session_end`, `subagent_start`, `subagent_stop`, `pre_compact`, `post_compact`). A `pre_tool_use` hook receives `{"tool","arguments"}` on stdin; a non-zero exit, a crash or a timeout **denies** with the hook's output as the model-visible detail (`run_pre_tool_hooks`, `exec_tools.rs:2353`). The other stages are notification-style (`run_notify_hooks`), never gate. `run_hook_once` redirects the hook's **stdout and stderr into one temp file**, so today a hook has no channel that could carry a structured result.
- **Plugin hooks** — `crates/plugin-host/src/hooks.rs`: a 27-event `HookEvent` engine (`ToolPre`, `ToolPost`, `ToolFailure`, `PermissionRequest`, `AgentStart/Stop`, …; `crates/plugin-host/src/hooks.rs:154–182`) with `HookSpec { matcher, timeout, failure_policy, requested_caps, sandbox }`, a `{"decision":"block"}` stdout parser (`parse_hook_output`), grant-attempt detection (invariant 13) and lease-gated execution through the process supervisor. It is reachable only from `rapid plugins hook-test` (a fixture dry-run); nothing in the exec loop dispatches it.

The exec loop already has the durable Human/Approval wait a hook `ask` needs: `permissions::Decision::Ask` → `ToolStepResult::ApprovalRequired` → the `SuspendedTurn` is persisted as the `approval.requested` payload → `TurnOutcome::Waiting` releases the lease → resolution (`/approvals`, ACP `acp_resolve_and_continue`) replays the suspension and executes the call exactly once (`apps/rapid/src/approvals.rs` module doc). `JsonlExitCode::NeedsApproval = 10` is the documented "needs a human" exit (`headless/jsonl.rs:104`).

## Decision

1. **One versioned result type, owned by `crates/protocol`.** `protocol::hooks::HookResult` (`schema = "rapidlm.hook_result"`, `version = 2`) is the wire shape a hook may print on **stdout**: `decision ∈ {allow, deny, ask, defer}`, `reason: Option<String>`, `updated_input: Option<Map>`, `additional_context: Option<String>`, `hook_specific: Option<Map>`. Unknown fields are ignored (additive evolution); a schema fixture lives under `crates/protocol/tests/fixtures/hooks/v2/`. The plugin-host engine's existing `"block"` token is accepted by the shared parser as a synonym of `deny` so that engine's tests keep their meaning; new hooks write the four v2 words.
2. **v1 semantics are the absence of a result.** A production hook that prints nothing parseable on stdout keeps today's contract byte-for-byte: exit code decides, stderr is the detail. `run_hook_once` therefore separates the two streams (stdout → result candidate, stderr → detail) and the pre-tool timeout/crash/malformed-output rules stay **deny**. Notification stages stay fail-open with a recorded warning.
3. **`ask` is the existing approval wait, not a new one.** A pre-tool `ask` is mapped onto `Decision::Ask` for that call with the hook's `reason` carried into the `ApprovalRequest` summary (after the call's own description) and the `approval.requested` payload (`source: "hook:<position>#<command digest>"`, `arguments_digest`: the SHA-256 of the arguments shown). On the approved resume the hooks run again; a hook's ask counts as answered only by an approval naming that hook and those exact arguments — a lattice approval, a different hook or different (rewritten) arguments raise their own question. The questions one stage raises about one call (an asking hook's, and a rewritten call's that needs a human) are about the same call as it would run, so they are raised as **one** request — the asking hook's reason leads — and one approval of that request — naming the hook whose question leads (the asking hook when one asks, else the rewriting hook) about those arguments — answers all of them; answered one at a time, each would re-raise the other on every resume. A hook that starts asking only on a later run is asked then: an approval of the rewrite's question is not its answer. Everything downstream — `approval.requested` → `tool.approval_required` (the `SuspendedTurn`) → `turn.interrupted[ApprovalPending]` → `/approvals` or ACP resolution → `approval.resolved` → continuation turn — is the existing path (S2, invariant 14). Headless `rapid exec` builds its tools without an approval sink today (`interactive.rs:8633–8636`), so a permission `Ask` becomes a model-visible `Denied(ModeAsk)` and the turn continues; that behaviour is unchanged (S11). A hook `ask` in headless is new behaviour and therefore gets the documented contract: the wait is recorded exactly as the TUI records it, the turn ends, and the process exits `NeedsApproval` (10) — never an implicit allow. It is resolved from a surface that can decide — `rapid resume <session>` then `/approvals`, or an ACP client; `rapid exec --continue` starts a new turn and does not resolve a pending approval (a headless `rapid approvals approve|deny` command is a SEAM-10 candidate). Unattended runs under a forced mode (`rapid cron`) install no hook-ask sink and keep the stated denial: a parked turn nobody resumes is worse.
4. **`defer` is "no opinion".** The call proceeds to the normal permission evaluation; the decision is still recorded (`hook.decided` event with `decision: defer`).
5. **Rewrites are validated, journaled and marked (S3).** `updated_input` replaces the call's arguments only after the rewritten arguments pass the same argument parser the tool uses at execution (`exec_tools` per-tool `parse_*_args`, `exec_tools.rs:2371–2385`, and the `MAX_TOOL_ARGUMENTS_BYTES` bound); a failure **denies naming the hook**. The governing document names `crates/tool-gateway` validation here; the audit found that crate is not a dependency of `apps/rapid` and `ExecTools::validate` is a pass-through (`exec_tools.rs:6927–6938`), so the per-tool parsers are the real contract today and wiring `tool-gateway` is out of this item's scope. The last rewriting hook wins; a `deny` from any hook discards every rewrite. A `hook.input_rewritten` ledger event carries hook id, every contributing hook (`contributors`: a chained rewrite is credited to each hook whose rewrite shaped the final input, in order), `sha256(before)`, `sha256(after)` and both bounded inputs; the transcript gets one line `[hook <contributors> rewrote <tool> input]`. A chain of rewrites that ends at exactly the arguments the model proposed is no rewrite. The permission decision is evaluated on the **rewritten** input (what will actually run): a deny denies; an Ask-class rewritten call is raised for a human (unless the call is `ask_user`) and runs only once an approval names this hook and these arguments; each hook in the stage sees the call as the hooks before it left it; an `updated_input` equal to what the hook was shown is not a rewrite.
6. **`additional_context` is untrusted tool-shaped content (S4).** It is appended *after* the tool result inside the fence the model already knows for untrusted material — `<untrusted_context locator="hook:<id>">…</untrusted_context>` (`apps/rapid/src/model.rs:530–537` uses this shape for `TrustClass::Untrusted` context blocks) — bounded by `MAX_HOOK_CONTEXT_BYTES` (4 KiB, the `MAX_READ_BYTES` ceiling; the audit found no single "tool-output ceiling" — bounds are per tool: 256 B detail, 4 KiB read, 8 KiB search, 16 KiB shell), and passes through the same redaction the result does. Instructions inside it are data; the locator in the fence's opening tag can carry no quote, angle bracket or line break. The bound is **per hook**: a stage of up to 8 hooks can add up to 8 fenced blocks. The fence is structural only if the text cannot close it, so the text is neutralised before wrapping (`model::fence_untrusted`, shared with retrieved context): any `<untrusted_context` / `</untrusted_context` in any case becomes `&lt;…`, and a line that begins `DATA_URL:` — which the request builder would turn into an image part — is renamed. Context follows a result the call produced: a `Succeeded` or `Failed` outcome, including the "invalid arguments" failure found after the pre stage ran. A call that produced none — denied, parked for approval, answered `ContextRequired`, or ended in a runtime error (`ToolStepError`) rather than a result — carries no context.
7. **New events are stages of the same config, not a new engine.** `user_prompt_submit` (a v2 `deny` blocks the prompt: the TUI shows the reason and puts the text back in the composer; a queued prompt that is blocked stays queued, *held* — carried over a restart, without holding up the messages queued after it — until `/queue edit` or `/queue run` retries it or `/queue cancel` drops it; the goal loop's compiled prompt passes the same gate, and a block stops the goal rather than being retried every tick; the loop decides nothing while a turn, a compaction or an unanswered approval holds the session, or before the TUI's projection holds every event the ledger does (the live tail delivers a poll interval late — deciding earlier would miss a turn's end or an approval it raised; the tip is one ledger query), and stops, saying so, when a protocol error has frozen that projection; it inspects each turn's transcript entries once, and a goal started while a turn runs stops if that turn ends interrupted or failed — as does one whose own iteration pauses for an approval (the paused turn ends interrupted); headless `rapid exec` prints the reason and exits `Policy` (3) before any model request; on the ACP (`session/prompt`) and `rapid daemon` (`turns.submit`) paths the gate runs before the prompt reaches the kernel, so a blocked prompt never becomes a turn — a failed turn's prompt would be part of the history the next turn replays to the model — and the client is refused with the reason (ACP: the reason as an agent message and stop reason `refusal`, judged only in a trusted project with prompt hooks, and only for a request the adapter would accept — initialized, well-formed, supported content within the size bound, an open session with no turn running and a binding to spare — otherwise the adapter's own error stands; the daemon: a JSON-RPC error, the decision recorded on the session, which moves it on — the client refreshes the session, the SDK's `Session.refresh()`, before its next submit; an unknown or closed session is the kernel's error and runs no hook). The daemon and headless `rapid exec` submit at a seq read before the gate ran — the client's `expected_seq`, the run's own read of the session, so a turn another writer recorded since still conflicts — and record an allowed prompt's decisions after the submit, accepted or not (recorded first, they would move the session past that seq; the hooks ran either way); the ACP adapter submits at the session's tip when it takes the prompt, so its gate records first; a resumed headless run whose submit conflicts — anything recorded on the session while the hooks ran — goes on unrecorded with a warning, as it did before the gate; `ask` has no one to ask — the prompt's author is the human — and is recorded without effect), `stop_cancelled` (fires *instead of* `stop` when a turn section ends without completing, with the stop reason's token — `cancelled` (an interrupt, also when it surfaces as an error), `approval_required`, `context_required`, `budget_exhausted`, `model_failed`, `tool_failed`, …, `failed` for an outcome with no stop reason, or `error`), `stop` (fires on a completed section). Each section of a TUI, continuation, ACP or daemon turn fires exactly one of the pair (headless `rapid exec` fires it where the run ends its turn; a few `--json-schema` error paths that return after the turn is recorded fire none — pre-existing, recorded as a follow-up): a turn that pauses for a human ends a section (`stop_cancelled` with `approval_required` or `context_required` — a pause, not an abort) and the continuation that resumes it is a section of its own. The turn-end helper runs where a section ends — headless, the TUI turn, a continuation — and each turn thread's wrapper fires the stage from the kernel outcome (counts 0) when a section ended before reaching it: an early failure (no credential, a context that cannot be built), a continuation that pauses again or is cancelled, a panic. `subagent_stop` gains the ability to block (a v2 `deny` replaces the child's report with a failure naming the hook, inline and detached — the detached path now fires `subagent_start`/`subagent_stop` at all, which it did not; the hook decides before anything the child wrote is applied — `SubagentRunner::settle` runs afterwards with how the child ended (`ChildEnd`): only a completed, unblocked child is applied (the runner's "effectively successful" child — tool calls, then an empty final message — counts as completed), and only headless; an interactive run holds what it does not apply for `/agents integrate|abandon`; a headless run discards a blocked or unfinished child's changes (nothing there could review or remove the worktree); a failed or cancelled child's are discarded everywhere, a hook's block notwithstanding (a cancellation that surfaces as an error, before the runner could clean up, is discarded by `settle`); `/agents` records what `settle` did — a child it applied or holds as completed ends *succeeded* — and before its end is recorded, so a blocked child ends *failed*), `post_tool_use_failure` (a failed call: context after the failure, cannot block; a call that fails with a runtime error other than a cancellation — no result, the turn ends — is observed too, with nothing deliverable; a command that exits non-zero is a completed call, observed by `post_tool_use`). Existing `session_start/end`, `pre/post_compact`, `subagent_start` stages are unchanged. These observing stages fail open: a hook that crashes, times out or prints an unreadable result is ignored with a recorded warning — `hook.failed` (`rapidlm.hook.failure/v1`: hook, stage, command digest, detail digest), plus a stderr line on headless. Payloads carry `event`; `stop`/`stop_cancelled` carry `tool_calls` and `tokens`.
8. **Managed policy narrows hooks.** A closed `[hooks]` table beside `[policy]` in the managed policy: `managed_only = true` runs only the hook lines the managed policy itself declares; `denied_events = [..]` skips stages by name; the policy may declare its own stage commands (at most 8 per stage, each non-empty and at most 512 bytes — refused otherwise, never dropped), which run first (an organisation's `pre_tool_use` gate decides before a project's). Both are gates in `managed_config.rs` (`gate_hooks`) reported with field/origin/remediation like the existing ones (S5), applied in `load_project_integrations` — the one loader every surface's hooks come from — on the merged settings, so neither settings file can widen them; `rapid doctor` warns with each report. A managed policy that cannot be loaded runs no project hooks (fail closed, reported).
9. **Provenance for every decision.** Every v2 decision — `allow` included, so AC-02's "ledger record" holds for all four words — appends `hook.decided` (`rapidlm.hook.decision/v1`: hook position `pre_tool_use[<n>]`, a 12-hex digest of the command line, event, decision, reason digest, grant-attempt flag, tool, call id). v1 hooks produce no record. In the transcript, `allow` and `defer` are silent; only a blocking or failing hook shows a line.

## What is deliberately not done

- The plugin-host `HookSpec` engine is **not** wired into the exec loop by this ADR. Its matcher, sandbox and lease model are the right long-term executor, but reaching it requires a lease at the call site (`sandbox_exec.rs`'s ceremony is the one production lease-minting path). The shared `protocol::hooks::HookResult` is the bridge: when the engine is wired later it parses the same shape. A second parser or a second decision enum is forbidden.
- No hook may grant a capability; a v2 object with grant-shaped keys is a recorded warning and the keys are ignored, as `plugin_host::hooks::is_grant_key` does today (invariant 13).

## Consequences

- `apps/rapid/src/hooks.rs` changes shape (separated streams, result parsing, new stages) and its module doc and constants lose the peer-product references they carry today (rule 2.4).
- `SEAM-05` (plan approval) and `SEAM-11` (elicitation) reuse decision 3's mapping onto the approval wait rather than adding a wait of their own.
- `docs/reference/event-catalog.md` gains `hook.decided`, `hook.input_rewritten`; `sdk/typescript/schemas/wire.v1.json` gains the same kinds (the SDK catalog is hand-maintained; there is no Rust→catalog drift test, so the delivery record names both edits).
