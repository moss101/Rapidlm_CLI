# Preregistration — verified orchestration vs. current RapidLM (`GVS-RAPIDLM-01`, GVS-003)

**Registered:** 2026-09-17, before any orchestration code lands (Phase 0). Changes after this date are appended as dated amendments, never edited in place.  
**Baseline audit:** [GVS-001](../goals/gvs5h-phase0-baseline-2026-09-17.md) · **Decision record:** [ADR 0021](../adrs/0021-verified-orchestration-extends-graph-and-supervisor.md)  
**Common gate:** the same one every evaluation spec here carries — deterministic assertions before model judges; exact fixture/version/model/prompt/context/tool schemas recorded; any security, data-loss, duplicate-effect or false-completion regression is a hard failure regardless of aggregate score.

## 1. Question and the two routes to "promote"

Does the verified workflow improve the reliability of substantial coding tasks over today's RapidLM turn at a comparable total budget — or reach the same reliability at a lower total cost? Exactly one of the two routes below must be declared *before* the release evaluation runs; the other is reported but does not decide.

| Route | Gate (frozen) |
|---|---|
| Quality at matched total budget | ≥ +5 percentage points verified success, paired 95% CI excluding zero |
| Efficiency at matched quality | ≥ 20% lower total measured cost per verified success, with a preregistered 2-point non-inferiority margin on success and the CI supporting it |
| Latency guard (both routes) | interactive p95 for substantial tasks ≤ 1.5 × baseline p95; routine `off`-mode tasks show no >5% median regression under repeated matched local conditions (investigated if seen) |
| Correctness guard (both routes) | every deterministic stale-evidence, false-acceptance, lost-candidate, policy and recovery case passes (the plan's §6 failure matrix); observed live false-acceptance rate reported with its interval, separately |

If neither route's gate is met, the outcome is **experimental-only / do-not-promote**: the feature stays `orchestration.mode = off` by default and nothing claims a proven improvement. Missing credentials, missing live runs, or incomplete platform checks are reported as missing evidence, never converted into a negative result.

## 3. Arms

| Arm | What runs | Answers |
|---|---|---|
| A | current RapidLM turn (`orchestration.mode = off`) | the actual product baseline |
| B | sequential plan → fresh worker with findings, no candidate preservation, no independent verifier | does the core GVS-inspired method add value? |
| C | B + immutable candidates/incumbent + independent verification + check receipts | do the proposed improvements help? |
| D | independent attempts with the same selector and checks as C, no shared findings | is the gain just extra sampling? |
| E | C with mixed-profile role routing (`ModelPurpose` per role) | does routing move the quality/cost frontier? |
| F (ablation) | fixed phase pipeline: localize → repair → validate, no manager decisions | does coordination earn its cost over a simple pipeline? |

Every requested arm is reported. An arm that cannot run (credentials, provider down, unknown name) is a typed skip in the result record and makes the run's exit nonzero (`eval_serve` already refuses unknown or empty arms); it is never counted as a pass or as "not different".

## 4. Statistics

- Unit of analysis: task. Repeated trials (three per task/arm initially) are clustered by task; repeats are not independent problems.
- Primary estimand: paired difference in verified-success rate (arm − A) with a task-level bootstrap 95% CI (10 000 resamples, seed recorded); secondary: cost per verified success (all attempts, all retries, planning, verification, compaction) with the same bootstrap.
- Sample size: the 24-task pilot estimates the variance; the held-out size (≥ 100) is confirmed or raised from that estimate for 80% power at the +5-point effect, and the number used is recorded as an amendment before the held-out run.
- No pooling across budget conditions; no exclusion of failed or infrastructure-classified tasks from the denominator without listing them; unknown usage stays unknown (never zero) and is reported as coverage.
- Latency: median and p95 wall-clock per task per arm; manager-call count, retries and context rebuilds reported alongside.

## 5. Provenance fields every result record must carry

`grading_version`, suite path and content hash, shard manifest (when sharded), commit (and `dirty` with a diff hash when dirty), arm name and version, resolved model identity for every role, provider/endpoint, sampling settings, context allowance, tool budgets, permission mode, per-task budget, exact invocation arguments, usage coverage, and for live runs the health-probe outcome. A record missing any of these is not admissible for the release decision.

## 6. Leakage and contamination controls

- Held-out tasks and their `verify`/`mutants` never appear in any packet handed to a worker or verifier; `protected` files are checked byte-for-byte after every run (grader v2).
- Generators self-check (setup fails, gold passes, gold kills every mutant) before a task is committed.
- Any known prior model exposure to a task's source material is recorded on the task; a pinned LiveCodeBench subset, if used, is secondary evidence only and states its grader differences from the official harness.
- No tuning against the held-out split; the development split is the only one consulted while implementing Phases 1–5.
