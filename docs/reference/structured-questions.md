# Structured questions

`ask_user` can request a version 1 form with one to four questions. Each question has an `id`, `question`, two to four options with unique `id` and `label`, and optional `header`, `multi_select`, and `allow_other`. An option can include a `description`. `allow_other` defaults to true. The existing single-question `question` and string `options` form remains supported.

Form answers, including free-text Other values, are recorded in the session ledger and sent to the model when the turn continues. These forms are not a secret-input mechanism; do not enter passwords, API keys, or other credentials.

For headless use, `rapid questions list <session-id> [offset]` prints JSON with the pending forms and `expected_seq`; use `next_offset` to page. Pipe a response into `rapid questions answer <session-id> <wait-token> <expected-seq>`. Partial responses are saved and leave the wait pending. A complete or cancelled response runs the continuation in the foreground and prints a JSON outcome; exit code 10 means it paused again for input. If an answer or cancellation was recorded but its continuation was not claimed, `rapid questions recover <session-id> <expected-seq>` starts that continuation. Refresh the sequence before each write. Answers are limited to 8192 UTF-8 bytes and are read from standard input.

In the interactive terminal, run `/approvals` to see the questions, option IDs and saved selections. Submit a JSON response with `/approvals answer <number> <json>`. For example, a partial answer to question `q1` is:

```text
/approvals answer 1 {"version":1,"status":"partial","answers":[{"question_id":"q1","selected":["a","b"]}]}
```

A partial response replaces the saved partial snapshot and leaves the question pending. Include all desired answers in each snapshot. To finish, submit `status: "complete"` with one answer for every question. A free-text choice uses `"other":"your text"` in the relevant answer; for a single-select question choose either one option or Other. A `{"version":1,"status":"cancelled","answers":[]}` response cancels the question as a denial.

The local daemon exposes pending structured forms and saved progress through `questions.list`; pass `offset` and follow `next_offset` when `truncated` is true. The TypeScript SDK exposes this as `session.questions({ offset })`. The local daemon accepts the same response object as the `answer` field of `approvals.resolve` with `decision: "approved"` and the current `expected_seq`. The TypeScript SDK exposes it through `session.approval({ decision: "approved", expected_seq, answer })`. Partial responses leave the wait pending. To cancel through the daemon, resolve with `decision: "denied"` and no answer. ACP clients that advertise form elicitation can answer a structured question through `elicitation/create`; clients without that capability cannot submit a structured answer through approval controls, so an unanswered question remains pending. On interactive session resume, a claim-aware answer or cancellation can be continued automatically if no later turn was started. Older unmarked cancellations are not automatically replayed. Once a continuation has been claimed, it is not automatically replayed after a crash because its effects may be uncertain.

After reconnecting to the daemon, refresh the session and call `session.recoverQuestion({ expected_seq })` to resume an answer or cancellation that was recorded but not claimed. The result is `started`, `none`, or `uncertain`. Subscribe to session events to follow a started continuation and refresh the session before further changes. An uncertain result means a claimed continuation may still be running or may have stopped after making changes; review it before retrying. It is not replayed automatically. A lost RPC response can also leave the outcome unknown, so refresh before attempting recovery again.

ACP clients can discover `rapidlm/questionRecovery` in the initialize capability `_meta` and send the extension request `_rapidlm/question_recover` with `{"sessionId":"..."}`. The request streams session updates and any further questions, then returns a prompt-style `stopReason`. A new ACP prompt is refused when it encounters an unclaimed recorded answer, so the client can recover that answer first. This is a Rapid-specific extension; clients that do not implement it can recover through the terminal or local SDK.
