# Multi-edit transaction constraints — REF-016

`workspace::TransactionManager` stages and verifies an in-memory overlay, but `materialize` explicitly permits `MaterializePartial` after a failed rename. It creates parent directories and writes sibling staging files before publishing, and the direct backend journal and checkpoints are in-memory. Neither mechanism alone provides crash recovery or the no-partial-application acceptance requirement for a model-facing multi-edit operation. `materialize` must not be exposed as atomic without additional recovery.

The implementation needs a bounded, versioned write-ahead transaction under trusted project-local state, storing the confined path identities, preimages and final bodies or durable staged references, file metadata, intent and progress. Resolve every path and permission independently, acquire shared per-path locks in a deterministic order, verify model-visible raw-byte preimages and all text-edit conflicts before modifying any target, and stage same-filesystem replacements before publishing. Persist and sync the transaction record and required directory metadata at each recovery boundary; on cancellation or a rename failure roll back every published target using verified preimages, and on the next trusted open recover an interrupted transaction before allowing conflicting writes. Preserve external changes by checking the exact expected postimage before rollback: an uncooperative external writer may prevent safe restoration, which must be reported as an explicit unresolved conflict rather than overwritten or described as success.

Multiple filesystem renames do not give atomic visibility to unrelated external readers; a durable rollback protocol can guarantee recovery and honest partial-conflict reporting, but must not claim an operating-system-wide multi-file atomic commit. Validate symlink confinement again at commit and recovery, preserve permissions, bound all bytes and paths, invalidate per-path read authority and evidence only after confirmed effects, and integrate existing approval, hooks, formatter and ledger behavior without letting one path approval widen another. Tests must cover conflicts before publication, injected failures at each publication boundary, cancellation, crash/restart at each journal phase, partial-recovery conflicts caused by external edits, parent-directory and permissions behavior, cleanup, and shared-path concurrency. No code currently satisfies this full acceptance.

## Production crash evidence and staging redesign

A killed-process test now exercises the actual workspace publication adapter, not the fixture adapter. After the first rename, reopening the workspace restores the original images and retains externally changed images as conflicts. However, the recovery journal is cleared while a later file's same-directory staging file remains. A second killed-process test invokes the actual staging adapter before intent publication: both staged files remain and the reopened workspace has no intent to recover. The staged file receives the target mode before the transaction commits; a leftover can therefore contain candidate content with those permissions. The tool must remain unadvertised while this remains.

A durable design must put a validated, unpredictable transaction identity and exact staging ownership into the intent before any stage is created, then persist the intent before staging. On restart, the recovery adapter must clean only artifacts provably belonging to that intent and sync their parent directories before removing the journal. It must tolerate an interrupted partial stage, refuse unexpected files or unsafe symlinks, preserve unrelated files even if names collide, and retain a recoverable journal whenever cleanup cannot be proven safe. A same-directory replacement is required for targets on different filesystems; placing all staged bytes under the journal directory alone does not guarantee same-filesystem rename. Tests need real process kills after intent, during each staging step, after each rename, during rollback, after commit and during cleanup, including preexisting/colliding names and external modification. The current lock coordinates participating RapidLM writers only; filesystem namespace replacement by uncooperative processes remains a separate unresolved race.

## Journal-first staging update

The internal Unix publisher now durably writes intent before creating stages, generates an OS-random transaction id, exclusively creates each empty stage, syncs its parent, and records device/inode identity in the journal before writing candidate bytes. Recovery removes a recorded stage only when its device/inode still match and its contents are a prefix of the intended image; unregistered paths, replaced stages and unexpected contents retain the intent and are not removed. Commit requires every replacement stage to be registered. Real-process kill tests verify recovery after staging and after the first published replacement, with no remaining tracked stages; external conflicts are preserved.

This does not close every crash boundary. A crash after creating an empty stage but before its identity is registered leaves an unregistered name that recovery cannot safely distinguish from a collision; it fails closed and retains the journal. Journal temporary-record cleanup, same-user hostile namespace replacement and inode reuse, complete crash-boundary testing, approvals, hooks and model-facing integration remain open. Legacy records without staging plans remain readable; old untracked stage files cannot safely be identified retroactively.
