# Structured questions — REF-019 in progress

RapidLM advertises a bounded version 1 form with one to four questions, single or multiple selections and optional Other text. The existing durable wait stores the exact tool call. Terminal `/approvals` displays every question and validated saved selection; invalid responses leave the wait open, partial snapshots are saved, and cancellation is recorded as a denial. `docs/reference/structured-questions.md` describes the response format.

Partial snapshots use an event append that checks the wait is pending and the expected ledger sequence in one transaction. A complete answer is stored atomically with the approval resolution; the continuation recovers it from that event and rejects an inconsistent in-memory answer. The tool call is selected from the latest matching exchange when an ID is reused. Focused current-source tests cover scripted tool-to-continuation flow, reopen of partial progress, cancellation, stale progress and refusal after resolution; full kernel and approval-flow snapshots also passed. See `structured_forms_terminal_partial` in validation.json.

REF-019 remains open. The local daemon and TypeScript SDK can submit partial and completed response objects; an approval without an answer leaves a question pending. ACP form elicitation is now wired when negotiated; its acceptance path still needs complete protocol integration tests. Headless-specific tests remain needed. A crash after resolution but before continuation is not automatically discovered and claimed; recovery must avoid duplicate effects. Full current-source workspace and platform acceptance remains REF-027.

Kimi's current documentation describes multiple questions, multiple selection and Other; it is supplementary to the pinned source analysis: https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/reference/tools.md and https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/reference/server-api.md.

ACP research: the current official ACP v2 schema includes `elicitation/create` with client capability negotiation and accept/decline/cancel actions; the live server now uses the existing v1/v2 negotiation adapter but still sends v1-style permission requests for questions. A permission choice cannot carry arbitrary multi-select and Other text. Implementing elicitation requires an explicit negotiated client capability, schema translation and validated response handling; clients without support must retain the pending wait and receive an explicit limitation. This is an implementation gap, not proof that every ACP client supports the newer protocol. Sources: https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/rfds/elicitation.mdx and https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/schema.mdx.

ACP v2 schema details: single selections can use string `oneOf` with titled const entries, while multiple selections use arrays with titled `anyOf` items. The restricted schema does not support nested objects or conditional validation, so Other must use a separate optional text field and the returned pair must be checked against the original question. Stable synthetic property keys avoid collisions between user-provided IDs. The client must advertise form elicitation before a request is sent; accept/decline/cancel are distinct. Source: https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/rfds/elicitation.mdx.

ACP recovery is a Rapid-specific extension because v1 `session/load` is specified as history replay, while a prompt has its own completion response. The [ACP session setup](https://agentclientprotocol.com/protocol/v1/session-setup) and [extension mechanism](https://agentclientprotocol.com/protocol/v1/extensibility) describe those boundaries. The kernel checks for a versioned unclaimed answer against the turn's expected sequence, and the append uses that same sequence, so a simultaneous answer resolution on another host conflicts rather than being silently superseded.
