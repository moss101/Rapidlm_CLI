# Video input: reference behavior and RapidLM design constraints

Reference revisions: `MoonshotAI/kimi-code` at `743f140978bddaf8b6aa524765fcd578f7c22fc9` and `agustif/opencode-v2` at `77bba6a46ac6aeb98362a55d017c8f83ba6f22eb`.

Kimi's `packages/kosong/src/message.ts` includes a `video_url` content part. Its `providers/kimi-files.ts` validates supported video extensions, reads bytes, sends an authenticated multipart file request with purpose `video`, and returns an `ms://` file identifier. Its `agent/media/mediaResolverService.ts` keys cached uploads by file, provider, protocol, origin and account identity, and checks video capability before resolving media. Its human media tool caps input at 100 MB. Google and Anthropic adapters also have provider-specific inline conversion. The OpenAI legacy and Responses paths replace unsupported media with text, and the resolver can produce a path tag on failure; RapidLM's acceptance explicitly requires an error rather than silent substitution. Kimi's observed uploader does not itself demonstrate a remote-delete/recovery protocol, so that lifecycle must be designed and verified independently rather than assumed.

OpenCode models retain input/output video modality metadata in `packages/opencode/src/provider/models.ts` and `provider.ts`; `provider/transform.ts` classifies video MIME types. This describes capabilities, not evidence that every provider accepts an arbitrary video attachment.

RapidLM's `crates/llm-router/src/provider.rs` currently models text, image artifacts and bounded inline image data only. Provider encoders and routing capability checks must reject unsupported video explicitly. Any new canonical video reference must bind a provider handle to the configured origin and credential identity, bound the path and bytes under workspace authority, avoid exposing handles across providers or accounts, and account for cancellation, ambiguous upload outcomes, remote cleanup and restart. Existing account egress gates and permission decisions must remain authoritative. No remote upload or deletion has been exercised against a live service.

Current implementation groundwork: canonical inline video supports declared video MIME types and at most 3 MiB of raw bytes, preserving the existing 8 MiB HTTP request bound. The native Google adapter accepts it only under an explicit programmatic video opt-in and encodes it as `inlineData`; non-user video parts and unsupported OpenAI-compatible or Anthropic routes are refused. The adapter uses the existing credential resolver and HTTP transport. The CLI now accepts bounded inline workspace video references with explicit model configuration, but does not yet supply uploads, durable cleanup or restart recovery. Google documents the Generate Content inline form and Files API in its [video guide](https://ai.google.dev/gemini-api/docs/generate-content/video-understanding) and [Files API reference](https://ai.google.dev/api/files); those docs do not establish a live RapidLM integration test.

File lifecycle groundwork: the provider transport now supports guarded, bodyless GET and DELETE without following redirects. Native Google file status and deletion use validated `files/<id>` names bound to the configured profile, credential handle and origin; processing state and returned name are checked. This is a library API, not an uploader or automatic cleanup. The binding uses the configured credential handle and cannot detect an account changing behind the same alias. Vertex file management, upload initiation/chunking, durable lifecycle records and credentialed live validation remain unimplemented.

Resumable-upload groundwork: native Google GenAI can now initiate an explicitly enabled video upload up to 100 MiB and submit bounded chunks through the existing authenticated, gated transport. The returned opaque upload URL must keep the exact initiating origin and path and is redacted from debug output. Chunks respect any reported granularity and the final accumulated SHA-256 must match the caller-supplied digest. Ambiguous exchanges mark the in-memory session uncertain and prevent blind retry. This low-level API is not connected to CLI attachments, file URI prompt delivery, durable upload recovery or automatic cleanup; a failure after remote creation can leave an orphan, and a mutable source can still change before all chunks are validated. Google documents the resumable start and finalize exchange in its [Files API reference](https://ai.google.dev/api/files). The chunk exchange was tested locally, not against a credentialed provider.

Uploaded-file inference: the native Google adapter constructs a provider-scoped canonical video part from a bound file handle. Before inference it rechecks the configured scope, resource path, active processing state and MIME type, and forwards the URI reported by the provider's metadata rather than constructing the inference URI itself. Missing, malformed, credential-bearing and HTTPS-downgrade URIs are refused; RapidLM does not dial the returned URI. Unsupported adapters refuse the part. Local HTTP fixtures exercise upload, status, inference and explicit deletion; the URI contract has not been verified against a live service. The CLI now uploads large files and can recover a subset of finalized cleanup records, as detailed in the continuation log.

Recovery prerequisite: the [Files API resource documentation](https://ai.google.dev/api/files) permits a client-supplied `files/<id>` at creation and limits the ID to 40 lowercase alphanumeric or dash characters. The adapter can start an upload with such a name and refuses a finalized response that names a different file. It can also check the file's reported MIME type, size and base64 SHA-256 against the original bytes. A future CLI lifecycle can persist a randomly generated name and its provider/account binding before the upload request, then reconcile an interrupted operation by name. This mechanism has only loopback and mock coverage; it does not establish that an interrupted resumable session is itself discoverable, that a 404 proves no later file can appear, or that a chosen name cannot collide with another client's file. Matching content is additional evidence, not proof of ownership, and recovery must not delete a file solely because its name matches an unverified local record.
