## Findings

1. **rapid with grok-build-0.1: 24–25 of 40 (60–63%)** across credential-clean
   runs — real model non-determinism between identical runs. Failure clusters:
   the `recovery` pipelines and `workflow` tasks (both need a shell call that
   acceptEdits denies), three `tests` tasks, and three `multifile` tasks.
2. **Grok CLI with `--always-approve`: 40/40, three times** (including the
   definitive same-window run). Its native auto-approval covers shell, which
   the workflow and recovery tasks need; rapid's acceptEdits denies shell —
   in the definitive run 9 of rapid's 16 non-passes were `shell_exec`
   denials. This is a **configuration asymmetry**, not evidence of a model
   or harness gap: the comparable rapid configuration (shell approved) was
   not available because rapid's approval ladder treats shell as a distinct
   grant.
3. **Both agents drive the same model family** (grok-build-0.1 via x.ai), so
   the delta is harness + approval configuration, not the model. In the
   definitive run both arms shared one window and fresh credentials, so the
   24/40 vs 40/40 delta is clean of auth effects — but still carries the
   approval-configuration asymmetry above, so it is not a like-for-like
   comparison and no superiority claim is made.
4. **Anthropic adapter has no streaming yet** (documented); the OpenAI-
   compatible path streams deltas live via the incremental SSE transport.
   End-to-end proof post parser-fix: `rapid exec` against the live x.ai
   endpoint printed tokens to stdout in 3 separate reads before the final
   answer (probe verdict `PROGRESSIVE`, 22 s wall); the TUI reducer replays
   coalesced `model.stream_delta` ledger events without blocking
   (`state.rs` replay test). `rapid exec` and interactive turns attach the
   same delta sink in production paths.
