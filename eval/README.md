# RapidLM evaluation program

Three suites, one grading pipeline (version 2), immutable result records.

| Directory | What it is | Generated by |
|---|---|---|
| `suite/` | **Representative** model-quality tasks — the default `rapid eval` suite. Independent tasks across five capability axes: `navigate` (unfamiliar multi-module code), `refactor` (genuine multi-file consolidation with drift), `context` (requirements scattered across many files), `errors` (recovery through failing tools and an interrupted refactor), `integration` (merging two branches / post-rename reconciliation). | `gen-repo-suite.py` |
| `suite-smoke/` | **Smoke** — 40 mechanical cases (bugfix/multifile/tests/recovery/workflow) that validate the harness end to end. Labelled smoke wherever reported; NOT a model-quality evaluation. | `gen-suite.py` |
| `suite-heldout/` | **Held-out** — same task shapes as `suite/`, never used for tuning. Run with `rapid eval --offline --suite eval/suite-heldout`. | `gen-repo-suite.py` (held-out section) |

## Grading (version 2)

Every task JSON carries `setup`, `prompt`, `gold`, `verify`, `verify_fails_before`,
and — since grading v2 — `protected` and `mutants`. All grading data lives in
the task file under `eval/`, never in the agent-editable scratch:

1. **Anti-vacuity** (before the agent works): `verify` must FAIL on the
   unmodified repo. A command that cannot execute (shell exit 126/127, spawn
   error) is typed `infrastructure`, never "failing test".
2. **Protected-file integrity** (after the run): every `protected` path must be
   byte-identical to its setup contents. Deletion counts. This rejects
   weakened tests, edited judges, and hard-coded harness files.
3. **Verification**: `verify` must pass on the submission.
4. **Mutation checks**: every entry in `mutants` is applied alone (a
   deliberately broken implementation); the submission's `verify` must FAIL
   against each. Empty test files, zero discovered tests, weakened assertions,
   and hard-coded outputs survive a mutant and are rejected. Pre-mutation
   contents are restored (or the file deleted) after each attempt.

Generators self-check every generation: setup-only must fail, gold must pass,
and gold must kill every mutant.

## Running

```
rapid eval --offline                          # gold trajectories through the real executor
rapid eval --live                             # model quality; health probe first; every requested arm reported
rapid eval --live --grant-shell --trials 3    # equal tool surface; repeated trials with variation reporting
rapid eval --offline --suite eval/suite-heldout
```

Exit code 0 only if EVERY task of EVERY requested arm passed. Skips fail the
gate: an empty, all-skipped, or incomplete comparison never passes.

## Live arms and honesty rules

`rapid` always runs; pinned competitors run only when the binary is present
AND reports the pinned version (see `RECIPES` in `apps/rapid/src/eval_serve.rs`;
pins dated 2026-09-15: grok 1.0.30, kimi 0.43.0, qwen 0.22.2). A dedicated
health probe (a trivial no-tools turn) gates each arm before any real task —
arm availability is a TYPED infrastructure outcome, never inferred from error
text. Arms that cannot run are recorded as skipped with the typed reason; they
are never omitted and never fabricated.

Same-model harness comparisons and default-model product comparisons must be
labelled as such in the analysis; the runner records the model and version of
every arm so the distinction is auditable after the fact.

## Provenance and accounting

Every results file (`eval/results/<mode>-<stamp>.json`) embeds a provenance
block: repository commit + dirty flag, runner version, grading version, suite
SHA-256 + task ids, resolved model identity, tool-permission configuration,
budgets, environment, and every arm's pinned vs observed version. Results are
append-only history; superseded claims are marked, never rewritten.

Accounting (per agent): the headline efficiency rate is TOTAL measured usage
across ALL attempts (passed and failed) divided by verified successes, with
coverage and a `lower_bound` flag when usage is missing; the successful-attempt
average is reported separately; measured cost and published-rate cost
estimates are kept in separate blocks and never merged. Verified successes
come from the grading pipeline, never from a turn merely completing.
